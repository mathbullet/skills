# Research

特定テーマについてWeb・論文・X等から多角的にソースを収集し、索引（.md）を作成する。

## 品質基準

以下を全ソースに適用する。

- 信頼できるソースを優先する（査読済み論文 > 公式ブログ > 主要テックメディア > 個人ブログ）
- 発信者が個人の場合、所属と役職を明記する。不明な場合は調査して埋める
- 論文の場合、書誌情報（著者、所属、発表venue、年）に加えて被引用数を明記する
- URLを必ず付与する
- 情報の日付を明記する
- 公式ドキュメントとサードパーティ記事は信頼度が異なる。混在させず、どちらの情報かを読み手が判別できるようにする

## 典拠・引用の規範

成果物中のすべての事実的記述には典拠を明示する。典拠のない記述は検証不能であり、レポートとしての価値がない。

### 参照の書式

- 本文中の参照は `[出所名, YYYY/MM]` の形式で記載する
- 番号参照（`[1]`, `[2]` 等）は使わない。番号だけでは読む側がいちいちソース一覧を往復しなければならず、可読性が低い
- 典拠を確認できなかった記述は、その旨を明記する（「典拠未確認」等）。黙って載せない

### 本文の構成: Assertion-Evidence形式

本文はAssertion-Evidence形式で書く。これは「まず主張を述べ、次にその根拠を示す」という構成である。

1. 地の文で、書き手自身の言葉による主張・要約を先に述べる
2. その直後に、主張を裏付けるソースからの原文引用をブロック引用で掲載する
3. 引用の直後に `[出所名, YYYY/MM]` を付す

読み手は「何が言いたいのか」を先に把握してから「その根拠は何か」を確認できる。逆順（引用が先、主張が後）は禁止する。引用を先に置くと、読み手はその引用が何のためにあるのかわからないまま読むことになる。

悪い例（引用が先）:

```
> The standard recipe of pretraining on trillions of tokens and then running RLHF
> with human preference labels is now considered dead.
>
> [llm-stats.com, 2026/03]

現在の主流はモジュラースタックに移行している。
```

良い例（主張が先）:

```
従来のRLHFパイプライン（人間の選好ラベル→報酬モデル→PPO）は主要モデルで使われなくなり、
機能を分離したモジュラースタックに置き換わった。

> The standard recipe of pretraining on trillions of tokens and then running RLHF
> with human preference labels is now considered dead. Every major model released
> in the past year uses a different post-training stack.
>
> 数兆トークンでの事前学習後にRLHFを走らせるという標準レシピはもはや死んだとみなされている。
> 過去1年にリリースされた全主要モデルが異なるポストトレーニングスタックを使用。
> [llm-stats.com, 2026/03]
```

### 引用の追加ルール

- 引用と地の文（書き手の要約・解釈）を明確に区別する
- 英語の引用には必ず日本語訳を付記する。原文の引用ブロックの直後に訳文を別行で添える形式とする。訳文を括弧で囲わない
- ブロック引用を使わない場合でも、ソースの主張と書き手の解釈が混同されない書き方にする

### ソース一覧の書式

`- [番号]` のリスト形式は使わない。以下の形式とする：

```
[参照ラベル, YYYY/MM] 著者. "タイトル." 媒体名. URL
```

## 見出しと内容の整合性

セクション見出しと、そのセクション内に配置する内容は厳密に一致しなければならない。

- 見出しが「人間側のガードレール」であれば、人間の行動・規律に関する内容のみを配置する。ツールやCI/CDの仕組みは別の見出しに分離する
- 見出しが「失敗事例」であれば、成功事例や推奨事項を混在させない
- あるソースが複数の観点にまたがる場合、観点ごとに分割して該当セクションに配置するか、最も適切なセクションに配置して他の観点は明示的に注記する
- 最終成果物を書き出す前に、各セクションの見出しとその配下の全項目が整合しているか確認する

## ワークフロー

1. ユーザーの依頼から [主張・仮説] と [収集対象] を特定する
2. 収集対象に応じた探索クエリを設計する（英語・日本語の両方）
3. サブエージェントに調査を委託する（観点別に並列化）
4. サブエージェントの出力を取りまとめ、メインエージェントが最終版を作成する
5. 成果物を .md ファイルとして書き出す

## サブエージェント委託のルール

調査をサブエージェントに委託するとき、以下を守る。

- サブエージェントには観点別に分割して並列に投げる（例: 「論文・学術」「メディア・ブログ」「X・コミュニティ」「産業動向」）
- 各サブエージェントには品質基準を明示的に伝える
- サブエージェントの出力はそのまま最終成果物にしない。メインエージェントが以下を行う:
  - 重複の除去
  - 情報の補完（所属・被引用数等の欠落を埋める追加調査）
  - 構造の統一（表形式、セクション構成の整理）
  - 批判・懸念の分離（肯定的証左と批判を明確に区別）
  - 調査上の制約の明記（取得できなかった情報、未検証のURL等）
  - 会話文脈からの独自解釈の除去（後述）
  - 見出しと内容の整合性チェック（前述）

## サブエージェントへの禁止事項

サブエージェントに以下を明示的に禁止する:

- 調査テーマの背景にあるユーザーのプロジェクトや目的を推測し、各ソースの説明に「○○との関連」「○○への応用」等の独自の関連づけを書かないこと
- ソースの説明はソース自体の内容に限定する。ソースに書かれていない解釈・接続・示唆を付加しない
- 悪い例: 「AI執筆改善との関連: フィードバックによる改善は勾配降下とは数学的に異なるプロセスであり...」（ソースにこの記述がないのに、会話の文脈から勝手に関連づけている）
- 良い例: 「主な批判点: 反転ラベルでも精度低下しないケースがあり、テキスト勾配は古典的な勾配降下と数学的に異なると指摘」（ソースの内容をそのまま記述している）

## 成果物の構造

```
# {テーマ}に関する調査レポート

調査日: YYYY-MM-DD
対象: {対象の説明}

## 1. {観点1}（例: 学術論文）
## 2. {観点2}（例: メディア報道）
## 3. {観点3}（例: X・コミュニティの反応）
## 4. {観点4}（例: 産業界シグナル）
## N. 批判・懸念
## N+1. 総合評価
## N+2. 調査上の制約
```

セクション構成はテーマに応じて柔軟に調整してよい。
